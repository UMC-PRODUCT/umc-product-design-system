결정마다 결정, 문제, 대안, 포기한 것, 성공 기준, 재검토 조건을 적습니다. 재검토 조건에 해당하는 일이 생기면 이 문서부터 고칩니다.

## 1. 컴포넌트 스타일은 미리 빌드한 CSS로 배포한다

- **결정**: 컴포넌트 CSS를 순수 CSS 파일로 미리 만들어 `@layer components`에 담고, 앱은 `@umc-product/react/styles.css`를 한 번 불러옵니다. 앱 쪽 수정은 `className`의 Tailwind 유틸리티로 합니다.
- **문제**: 컴포넌트가 Tailwind 클래스 문자열을 품으면 앱의 Tailwind 설정(`@source` 경로, 버전, 접두사)이 컴포넌트 모양을 좌우합니다. CSS-in-JS 런타임은 서버 컴포넌트에서 쓰기 어렵습니다.
- **대안**: shadcn처럼 Tailwind 클래스를 컴포넌트에 넣고 앱이 소스를 스캔하는 방식, vanilla-extract 빌드, CSS Modules
- **포기한 것**: 컴포넌트 안에서 유틸리티를 바로 쓰는 편의, 쓰지 않는 컴포넌트 CSS를 빼는 최적화
- **성공 기준**: 앱이 import 순서를 바꿔도 유틸리티가 컴포넌트를 이깁니다(`tailwind.test.ts`). 병합 함수 없이 `className`만으로 덮어씁니다.
- **재검토 조건**: 소비 앱이 Tailwind를 떠나거나, 컴포넌트 CSS가 커져 첫 화면 로딩을 늦출 때

shadcn 방식은 소비 앱이 하나뿐이고 디자인 시스템과 같은 저장소에 있을 때 더 낫습니다. 이번에는 패키지로 배포해 여러 앱이 쓰는 상황을 전제로 했습니다.

## 2. 상호작용 컴포넌트는 Base UI로 만든다

- **결정**: 포커스 이동, 키보드, ARIA가 필요한 컴포넌트(Select, Menu, Tabs, Tooltip, Toast, Number Field, OTP Field, Radio Group, Checkbox Group)는 `@base-ui/react` 1.8로 만듭니다. 모양은 Base UI가 다는 data 속성으로 꾸밉니다.
- **문제**: 접근성 동작을 직접 만들면 키보드와 화면 낭독기 버그가 쌓이고, 검증할 테스트도 크게 늘어납니다.
- **대안**: Radix UI, React Aria, 직접 구현
- **포기한 것**: 의존성 하나와 Base UI 메이저 업그레이드 비용, Radix의 넓은 생태계
- **성공 기준**: 모든 동작을 키보드만으로 할 수 있고, 컴포넌트마다 역할과 이름으로 찾는 동작 테스트가 통과합니다.
- **재검토 조건**: Base UI에 필요한 부품이 없거나 API가 자주 깨질 때

React Aria는 날짜, 숫자 국제화와 터치 동작이 중요한 컴포넌트가 늘어날 때 더 낫습니다.

## 3. 피그마 값은 3단계 규칙으로 옮긴다

- **결정**: 피그마가 3기 변수를 연결한 값은 토큰으로 씁니다. 이름 있는 스타일(텍스트 스타일, 그림자)은 토큰 패키지에 넣어 씁니다. 나머지는 피그마 값을 그대로 `--umc-<component>-<role>` 변수에 담고 확인 목록에 적습니다.
- **문제**: 피그마에 2기 값, 스타일을 덮어쓴 값, 이름 없는 값이 섞여 있습니다. 가까운 토큰으로 바꾸면 피그마와 어긋나고, 리터럴을 흩어 두면 나중에 토큰으로 옮길 곳을 찾기 어렵습니다.
- **대안**: 가장 가까운 토큰으로 맞추기, 모든 값을 리터럴로 두기
- **포기한 것**: 일부 컴포넌트에 리터럴이 남습니다. 대신 역할 변수 선언 한 곳에만 둡니다.
- **성공 기준**: 색 리터럴이 역할 변수 선언에만 있습니다(`css-contract.test.ts`). 문서의 `figma-spec.json` 대조에서 불일치가 0건입니다.
- **재검토 조건**: 디자인 팀이 확인 목록의 값을 3기 변수로 다시 연결하면 역할 변수를 토큰으로 바꿉니다.

## 4. 토큰, 아이콘, 컴포넌트를 세 패키지로 나눈다

- **결정**: `@umc-product/design-tokens`, `@umc-product/icons`, `@umc-product/react`로 나눕니다. 컴포넌트 패키지 안은 그룹 폴더(forms, selection, overlay, shell)로 나누고, 그룹마다 `index.ts`와 그룹 CSS를 따로 둡니다.
- **문제**: 아이콘은 컴포넌트 없이도 쓰이고 생성 과정이 다릅니다. 컴포넌트를 그룹별로 나눠 동시에 만들 때 공유 파일을 함께 고치면 충돌이 납니다.
- **대안**: 패키지 하나로 합치기, 컴포넌트마다 패키지
- **포기한 것**: 패키지 사이 버전을 맞추는 비용
- **성공 기준**: 그룹 브랜치를 병합할 때 공유 파일 충돌이 없습니다. 아이콘만 쓰는 앱은 컴포넌트 패키지를 설치하지 않습니다.
- **재검토 조건**: 배포를 시작해 패키지별 버전과 변경 기록이 필요할 때, 그룹보다 작은 단위의 진입점이 필요할 때

## 5. 피그마 속성 이름을 정해진 표로 코드 이름에 대응시킨다

- **결정**: 디자인 팀 노션의 명명 규칙을 기준으로 대응표를 둡니다. `Size`는 `size`, `Style`은 `variant`, `State`는 prop 없이 CSS 상태, `Error`는 `invalid`와 `errorMessage`로 옮깁니다. 전체 표는 [컴포넌트 구현 규칙](/contributing/component-guide/)에 있습니다.
- **문제**: 피그마 속성 이름이 컴포넌트마다 다르고 오타(`Varient`, `Disalbed`)가 섞여 있습니다. 이름을 그대로 옮기면 같은 뜻의 prop이 컴포넌트마다 달라집니다.
- **대안**: 피그마 속성 이름을 그대로 쓰기
- **포기한 것**: 피그마와 코드의 이름이 일대일로 같지 않습니다(`Style`과 `variant`). React의 `style` prop과 겹치지 않게 하려는 선택입니다.
- **성공 기준**: 같은 뜻의 prop이 모든 컴포넌트에서 같은 이름과 같은 값 목록을 씁니다.
- **재검토 조건**: 디자인 팀이 명명 규칙을 바꾸거나 Code Connect를 붙일 때

## 6. 아이콘은 직접 만든 변환기로 생성한다

- **결정**: 피그마 SVG 원문을 sha256과 함께 보관하고, 직접 만든 파서와 변환기로 React 컴포넌트를 생성합니다. 규칙 밖의 원문이 들어오면 노드 이름과 함께 생성을 멈춥니다.
- **문제**: 피그마 내보내기가 아이콘마다 다릅니다. 프레임 대신 안쪽 도형만 내보내거나, 프레임이 정사각형이 아니거나, 색이 여러 개입니다. 이런 원문을 조용히 통과시키면 모양이 어긋난 채 배포됩니다.
- **대안**: SVGO와 SVGR로 일괄 변환
- **포기한 것**: SVGO의 경로 최적화로 줄일 수 있는 파일 크기
- **성공 기준**: `pnpm icons:check`로 재생성 결과가 커밋된 파일과 같습니다. 문서 대조에서 아이콘 위치가 피그마와 0.2px 안에서 맞습니다.
- **재검토 조건**: 아이콘이 수백 개로 늘어 번들 크기가 문제가 될 때. 그때는 변환기 앞에 SVGO 경로 최적화를 붙입니다.
