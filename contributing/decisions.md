# 결정 기록

디자인 시스템을 만들며 되돌리기 어려운 결정 9개를 ADR 형식으로 남깁니다.

- 독자: 디자인 시스템을 고치거나 쓰는 개발자
- 소유자: UMC PRODUCT Design Chapter
- 기준일: 2026-10-18

결정마다 결정, 문제, 대안, 포기한 것, 성공 기준, 재검토 조건을 적습니다. 재검토 조건에 해당하는 일이 생기면 이 문서부터 고칩니다.

## 1. 컴포넌트 스타일은 미리 빌드한 CSS로 배포한다

- **결정**: 컴포넌트 CSS를 순수 CSS 파일로 미리 만들어 `@layer components`에 담고, 앱은 `@umc-product/react/styles.css`를 한 번 불러옵니다. 앱 쪽 수정은 `className`의 Tailwind 유틸리티로 합니다.
- **문제**: 컴포넌트가 Tailwind 클래스 문자열을 품으면 앱의 Tailwind 설정(`@source` 경로, 버전, 접두사)이 컴포넌트 모양을 좌우합니다. CSS-in-JS 런타임은 서버 컴포넌트에서 쓰기 어렵습니다.
- **대안**: shadcn처럼 Tailwind 클래스를 컴포넌트에 넣고 앱이 소스를 스캔하는 방식, vanilla-extract 빌드, CSS Modules
- **포기한 것**: 컴포넌트 안에서 유틸리티를 바로 쓰는 편의, 쓰지 않는 컴포넌트 CSS를 빼는 최적화
- **성공 기준**: 앱이 import 순서를 바꿔도 유틸리티가 컴포넌트를 이깁니다(`tailwind.test.ts`). 병합 함수 없이 `className`만으로 덮어씁니다.
- **재검토 조건**: 소비 앱이 Tailwind를 떠나거나, 컴포넌트 CSS가 커져 첫 화면 로딩을 늦출 때

shadcn 방식은 소비 앱이 하나뿐이고 디자인 시스템과 같은 저장소에 있을 때 더 낫습니다. 이번에는 패키지로 배포해 여러 앱이 쓰는 상황을 전제로 했습니다.

## 2. 상호작용 컴포넌트는 Base UI로 만든다

- **결정**: 포커스 이동, 키보드, ARIA가 필요한 컴포넌트(Select, Menu, Tabs, Tooltip, Toast, Number Field, OTP Field, Radio Group, Checkbox Group)는 `@base-ui/react` 1.8로 만듭니다. 모양은 Base UI가 다는 data 속성으로 꾸밉니다.
- **문제**: 접근성 동작을 직접 만들면 키보드와 화면 낭독기 버그가 쌓이고, 검증할 테스트도 크게 늘어납니다.
- **대안**: Radix UI, React Aria, 직접 구현
- **포기한 것**: 의존성 하나와 Base UI 메이저 업그레이드 비용, Radix의 넓은 생태계
- **성공 기준**: 모든 동작을 키보드만으로 할 수 있고, 컴포넌트마다 역할과 이름으로 찾는 동작 테스트가 통과합니다.
- **재검토 조건**: Base UI에 필요한 부품이 없거나 API가 자주 깨질 때

React Aria는 날짜, 숫자 국제화와 터치 동작이 중요한 컴포넌트가 늘어날 때 더 낫습니다.

## 3. 피그마 값은 3단계 규칙으로 옮긴다

- **결정**: 피그마가 3기 변수를 연결한 값은 토큰으로 씁니다. 이름 있는 스타일(텍스트 스타일, 그림자)은 토큰 패키지에 넣어 씁니다. 나머지는 피그마 값을 그대로 `--umc-<component>-<role>` 변수에 담고 확인 목록에 적습니다.
- **문제**: 피그마에 2기 값, 스타일을 덮어쓴 값, 이름 없는 값이 섞여 있습니다. 가까운 토큰으로 바꾸면 피그마와 어긋나고, 리터럴을 흩어 두면 나중에 토큰으로 옮길 곳을 찾기 어렵습니다.
- **대안**: 가장 가까운 토큰으로 맞추기, 모든 값을 리터럴로 두기
- **포기한 것**: 일부 컴포넌트에 리터럴이 남습니다. 대신 역할 변수 선언 한 곳에만 둡니다.
- **성공 기준**: 색 리터럴이 역할 변수 선언에만 있습니다(`css-contract.test.ts`). 문서의 `figma-spec.json` 대조에서 불일치가 0건입니다.
- **재검토 조건**: 디자인 팀이 확인 목록의 값을 3기 변수로 다시 연결하면 역할 변수를 토큰으로 바꿉니다.

## 4. 토큰, 아이콘, 컴포넌트를 세 패키지로 나눈다

- **결정**: `@umc-product/design-tokens`, `@umc-product/icons`, `@umc-product/react`로 나눕니다. 컴포넌트 패키지 안은 그룹 폴더(forms, selection, display, overlay, shell)로 나누고, 그룹마다 `index.ts`와 그룹 CSS를 따로 둡니다.
- **문제**: 아이콘은 컴포넌트 없이도 쓰이고 생성 과정이 다릅니다. 컴포넌트를 그룹별로 나눠 동시에 만들 때 공유 파일을 함께 고치면 충돌이 납니다.
- **대안**: 패키지 하나로 합치기, 컴포넌트마다 패키지
- **포기한 것**: 패키지 사이 버전을 맞추는 비용
- **성공 기준**: 그룹 브랜치를 병합할 때 공유 파일 충돌이 없습니다. 아이콘만 쓰는 앱은 컴포넌트 패키지를 설치하지 않습니다.
- **재검토 조건**: 배포를 시작해 패키지별 버전과 변경 기록이 필요할 때, 그룹보다 작은 단위의 진입점이 필요할 때

## 5. 피그마 속성 이름을 정해진 표로 코드 이름에 대응시킨다

- **결정**: 디자인 팀 노션의 명명 규칙을 기준으로 대응표를 둡니다. `Size`는 `size`, `Style`은 `variant`, `State`는 prop 없이 CSS 상태, `Error`는 `invalid`와 `errorMessage`로 옮깁니다. 전체 표는 [컴포넌트 구현 규칙](./component-guide.md)에 있습니다.
- **문제**: 피그마 속성 이름이 컴포넌트마다 다르고 오타(`Varient`, `Disalbed`)가 섞여 있습니다. 이름을 그대로 옮기면 같은 뜻의 prop이 컴포넌트마다 달라집니다.
- **대안**: 피그마 속성 이름을 그대로 쓰기
- **포기한 것**: 피그마와 코드의 이름이 일대일로 같지 않습니다(`Style`과 `variant`). React의 `style` prop과 겹치지 않게 하려는 선택입니다.
- **성공 기준**: 같은 뜻의 prop이 모든 컴포넌트에서 같은 이름과 같은 값 목록을 씁니다.
- **재검토 조건**: 디자인 팀이 명명 규칙을 바꾸거나 Code Connect를 붙일 때

## 6. 아이콘은 직접 만든 변환기로 생성한다

- **결정**: 피그마 SVG 원문을 sha256과 함께 보관하고, 직접 만든 파서와 변환기로 React 컴포넌트를 생성합니다. 규칙 밖의 원문이 들어오면 노드 이름과 함께 생성을 멈춥니다.
- **문제**: 피그마 내보내기가 아이콘마다 다릅니다. 프레임 대신 안쪽 도형만 내보내거나, 프레임이 정사각형이 아니거나, 색이 여러 개입니다. 이런 원문을 조용히 통과시키면 모양이 어긋난 채 배포됩니다.
- **대안**: SVGO와 SVGR로 일괄 변환
- **포기한 것**: SVGO의 경로 최적화로 줄일 수 있는 파일 크기
- **성공 기준**: `pnpm icons:check`로 재생성 결과가 커밋된 파일과 같습니다. 문서 대조에서 아이콘 위치가 피그마와 0.2px 안에서 맞습니다.
- **재검토 조건**: 아이콘이 수백 개로 늘어 번들 크기가 문제가 될 때. 그때는 변환기 앞에 SVGO 경로 최적화를 붙입니다.

## 7. 토큰 이름은 피그마 변수 이름을 그대로 따른다

- **결정**: 토큰 이름은 피그마 변수 경로를 kebab-case로 바꾼 것이고 단계 숫자도 남깁니다(`Fill/Neutral/Weak-75` → `--umc-color-fill-neutral-weak-75`). Tailwind에서 Text와 Border는 `text-<이름>`, `border-<이름>` 속성 클래스로만 만듭니다. 나머지 semantic과 primitive는 Tailwind 색으로 등록하고 기본 팔레트는 지웁니다.
- **문제**: 피그마를 보고 구현하려면 이름을 두 번 바꿔야 했습니다. `Text/Neutral-Medium-600`이 토큰에서는 단계 숫자를 뺀 `neutral-medium`, Tailwind에서는 그룹 이름을 바꾼 `text-fg-neutral-medium`이었습니다. primitive는 클래스가 없는데 기본 팔레트가 남아 있어서, `text-teal-300`이 오류 없이 Tailwind의 teal을 칠했습니다. 피그마 컴포넌트는 primitive를 바로 칠한 곳이 많습니다(Text Button `Teal-700`, Checkbox `Red-400`).
- **대안**: 모든 그룹을 Tailwind 색으로 등록하기(`text-text-…`, `border-border-…`), Text 그룹만 `fg`로 바꾸기(이전 방식), 피그마 Dev Mode의 codeSyntax 이름 쓰기, 단계 숫자 빼기
- **포기한 것**: Text·Border 색에는 불투명도 수식어(`/50`)와 outline, ring 같은 다른 속성 클래스가 없습니다. 이런 곳은 `outline-(--umc-color-border-primary-strong-500)`처럼 CSS 변수로 씁니다. 기본 팔레트에 기대던 앱 코드는 `@theme`으로 색을 다시 등록해야 합니다. 피그마에서 변수 값만 바꾸면 이름의 단계 숫자와 실제 값이 어긋날 수 있습니다.
- **성공 기준**: 피그마 변수 이름과 [Tailwind 대응 표](https://umc-product.github.io/umc-product-design-system/getting-started/tailwind/) 하나로 클래스를 맞힙니다. 그룹 이름이 겹친 클래스와 피그마에 없는 기본 팔레트 클래스는 생성되지 않습니다(`outputs.test.ts`).
- **재검토 조건**: 디자인 팀이 codeSyntax를 변수마다 다른 `var(--umc-color-…)`로 정리할 때, 다크 모드처럼 모드가 생길 때, Text·Border 색을 다른 속성에 쓰는 코드가 늘어날 때

codeSyntax 이름은 변수마다 유일해지면 더 낫습니다. Dev Mode 코드 패널을 그대로 옮겨도 되기 때문입니다. 지금은 `var(--color-action-primary-default)` 하나를 변수 31개가 나눠 써서 색을 가리키지 못합니다.

## 8. 패키지는 GitHub Packages에 비공개로 배포하고, 사용 권한은 라이선스로 제한한다

- **결정**
  - 세 패키지를 GitHub Packages(`npm.pkg.github.com`)에 비공개로 배포하고, changesets의 `fixed`로 같은 버전을 붙입니다. react는 토큰과 아이콘을 같은 minor 범위(`^0.1.0`)로 의존합니다.
  - 저장소는 공개로 두고, 사용 권한은 커스텀 라이선스([LICENSE](https://github.com/UMC-PRODUCT/umc-product-design-system/blob/develop/LICENSE))로 UMC PRODUCT Design Chapter가 허락한 사람과 팀에만 줍니다. 기여자는 자기 기여물의 권리와 포트폴리오 활용을 그대로 가집니다.
  - 문서(GitHub Pages)를 먼저 공개하고, 패키지는 첫 릴리스 때 배포합니다. 기본 브랜치는 develop이고, 첫 릴리스 뒤에는 main 병합이 곧 배포입니다.
- **문제**: 패키지를 워크스페이스 안에서만 설치할 수 있어서, 팀마다 새로 만들 FE 저장소가 쓰지 못합니다. 배포 경로가 없으니 버전과 변경 기록도 없었습니다.
- **대안**: npm 비공개 패키지(조직 멤버마다 월 $7), 저장소를 비공개로 돌리고 문서는 Amplify에 배포, npm 공개 배포, git URL 의존성
- **포기한 것**
  - 소스 보호: 저장소가 공개라 누구나 소스를 볼 수 있고, 사용 제한은 라이선스에만 기댑니다. 공개 문서와 배포된 앱이 내려보내는 CSS·JS는 어느 방식으로도 숨길 수 없습니다.
  - 인증 없는 설치: GitHub Packages는 설치에 토큰이 필요합니다.
  - 패키지별 버전: 토큰 패키지만 바뀌어도 세 패키지가 함께 올라갑니다.
- **성공 기준**: 깨끗한 폴더에서 `.npmrc` 한 줄과 GitHub 토큰만으로 설치하고 빌드합니다(`scripts/smoke-consumer.mjs`가 같은 과정을 tarball로 검사). main 병합 한 번으로 패키지와 문서가 함께 배포됩니다.
- **재검토 조건**: 소스까지 숨겨야 할 때, 조직 밖에 공개해야 하거나 Actions 밖 전송량이 월 1GB에 가까워질 때, 세 패키지의 변경 주기가 크게 갈라질 때

소스까지 숨겨야 하면 저장소를 비공개로 돌리고 문서를 Amplify 같은 다른 곳에 올립니다. Free 플랜에서는 비공개 저장소의 Pages를 쓸 수 없기 때문입니다. GitHub Packages의 패키지는 공개로 바꾸면 되돌릴 수 없으므로, 공개가 필요해지면 GitHub Packages에서 바꾸지 말고 npm 공개 배포와 함께 다시 결정합니다.

## 9. Storybook은 별도 앱으로 두고 컴포넌트 소스를 직접 읽는다

- **결정**
  - Storybook을 비공개 워크스페이스 앱 `apps/storybook`에 둡니다. 배포는 문서 사이트와 같은 AWS Amplify 앱이 맡아, 문서 기준 경로 아래 `storybook/`(`/design-system/storybook/`)에 함께 올립니다.
  - Vite alias로 `@umc-product/react`를 `packages/react/src`에 연결해 props 타입에서 Controls를 만듭니다. 토큰과 아이콘은 빌드한 `dist`를 씁니다.
  - 컴포넌트마다 Playground 스토리를 기본으로 둡니다. 피그마 변형 그리드는 Storybook에 다시 만들지 않고 문서 페이지로 연결하며, 문서 앱의 코드는 가져다 쓰지 않습니다.
  - 공개 사이트에 피그마 링크를 노출하지 않도록 피그마 패널(addon-designs)은 넣지 않습니다.
- **문제**: 디자이너가 문서 사이트에서는 props를 바꿔 보거나 원하는 조합에 hover와 focus를 켜 볼 수 없었습니다.
- **대안**: 스토리를 `packages/react/src`의 컴포넌트 옆에 두기, 문서 사이트에 Playground 예시 더하기, 문서의 변형 그리드를 Storybook에서 재사용하기, Storybook을 별도 Amplify 앱으로 배포하기, Chromatic 같은 Storybook 전용 호스팅
- **포기한 것**
  - 컴포넌트 옆에 스토리를 두는 응집: 패키지 안에 두면 tsc 빌드가 스토리를 `dist`에 넣고, use-client 계약 테스트에도 걸립니다.
  - Storybook 안에서 모든 변형 보기: 문서 그리드를 재사용하면 두 앱이 문서의 CSS, 코드 툴팁 플러그인, 상태 강제 스크립트를 함께 써야 합니다. 그러면 한쪽을 고칠 때 다른 쪽이 깨집니다.
  - 배포 전 미리보기: 기본은 main 브랜치만 배포하므로 병합한 뒤에야 바뀐 모습을 봅니다.
  - Storybook만 따로 배포하기: 문서와 한 빌드로 묶여서 Storybook 빌드가 깨지면 문서도 배포하지 않습니다. 빌드 시간도 Storybook 빌드만큼 늘어납니다.
- **성공 기준**: export한 모든 컴포넌트와 `figma-spec.json`이 있는 모든 컴포넌트에 스토리가 있고 jsdom에서 렌더됩니다(`apps/storybook/src/stories.test.tsx`). 배포할 패키지에 스토리 파일이 들어가지 않습니다. 문서와 Storybook이 한 도메인의 `/design-system/`과 `/design-system/storybook/`에서 열립니다.
- **재검토 조건**: 디자이너가 배포 전 검토를 원할 때, 스토리와 문서 예시를 함께 고치는 일이 잦아질 때, Storybook을 거의 쓰지 않을 때, Storybook을 문서와 다른 주소나 다른 주기로 배포해야 할 때

배포 전 검토가 필요해지면 Amplify에 develop 브랜치나 PR 미리보기를 연결합니다. 화면 변화를 승인하는 흐름까지 필요하면 Chromatic이 더 낫습니다.

Storybook을 별도 Amplify 앱으로 두는 쪽은 Storybook을 서브도메인처럼 문서와 다른 주소에 둘 때 더 낫습니다. Amplify의 사용자 지정 도메인은 앱 하나에만 붙고 Amplify 앱 사이의 rewrite도 기대기 어려워서, 한 도메인의 두 경로로 나누려면 앞단에 CloudFront 같은 프록시가 필요합니다.

## 10. 질문지는 통째 빌더가 아니라 부품으로 만든다

- **결정**
  - 피그마 `Form`(질문지)을 질문(`FormQuestion`)과 답 부품(`FormTextAnswer`, `FormChoiceList`, `FormAttachmentField`), 질문지 편집 부품으로 나눠 냅니다. 새 문서 그룹 "질문지"에 둡니다.
  - 질문 목록 상태, 편집 중인 질문(`active`), 질문마다 어떤 답 부품을 쓸지, 순서 변경, 파일 업로드, 링크를 첨부로 확정하는 시점, 서버 저장은 앱이 맡습니다. 문항 유형 목록도 앱이 넘깁니다.
  - 질문 제목과 설명을 답 칸의 이름과 설명으로 잇는 일, 필수와 읽기 전용, 비활성을 답 칸에 전하는 일은 `FormQuestion`이 맡습니다.
- **문제**: 피그마 `Form`은 프로젝트 지원 질문과 리크루팅 문항을 함께 담는 질문지 편집기입니다. web-v2에는 두 화면이 이미 서로 다른 질문 모델로 있고, 리크루팅 API 계약은 아직 바뀌고 있습니다.
- **대안**: 질문 스키마를 받아 질문지 전체를 그리는 빌더 컴포넌트, 디자인 시스템은 기존 입력 부품만 주고 질문지는 앱이 모두 만들기
- **포기한 것**
  - 앱이 할 일이 가장 적은 빌더: 디자인 시스템이 서버 질문 모델에 묶이면 모델이 바뀔 때마다 디자인 시스템 배포가 필요합니다.
  - 질문 목록 조립 코드의 중복: 화면마다 질문 유형에 맞는 답 부품을 고르는 코드가 생깁니다.
  - 순서 변경 동작의 일관성: 끌어서 옮기는 동작은 앱이 붙이므로 화면마다 다를 수 있습니다.
- **성공 기준**: web-v2의 프로젝트 지원 질문과 리크루팅 문항 화면이 같은 부품으로 그려지고, 질문 모델이 바뀌어도 디자인 시스템을 고치지 않습니다. 질문 제목이 답 칸의 접근 가능한 이름이 되는 것을 테스트로 지킵니다.
- **재검토 조건**: 두 화면의 조립 코드가 거의 같아질 때, 서버 질문 모델이 확정되어 잘 바뀌지 않을 때, 세 번째 질문지 화면이 생길 때

두 화면이 같은 순서로 같은 부품을 조립하게 되면 그 조립을 빌더로 묶는 쪽이 낫습니다. 그때는 빌더를 부품 위에 얹어, 부품을 직접 쓰는 화면도 계속 지원합니다.
